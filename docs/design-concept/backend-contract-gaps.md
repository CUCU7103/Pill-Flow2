# 디자인 시안과 데이터 계약의 차이

작성일: 2026-09-25 · 범위: PillFlow 리디자인 구현

이 문서는 디자인 작업 중 발견한 데이터/플랫폼 계약의 차이를 기록한다. 화면 작업은 현재 동작 가능한 범위에서 진행했다. 원격 Supabase 스키마와 운영 데이터는 이 작업에서 직접 확인하지 않았으므로, 아래 내용은 저장소 코드 기준이다.

## 1. 여러 복용 시간에 대한 완료 상태

- **시안 기대:** 한 약을 하루 여러 번 복용한다면 각 시간의 완료 여부를 따로 표시하고 완료할 수 있다.
- **현재 계약:** `Medication.times`는 여러 시간을 지원하지만 `medicationRepository.toggleMedicationLog()`는 `medication_id`와 `date`만으로 오늘 로그를 삽입/삭제한다. `fetchMedications()`도 약별 오늘 완료 여부 하나만 반환한다. 알림은 `notificationSchedule.ts`에서 시간마다 예약한다.
- **이번 구현:** 오늘 화면의 복용 완료/취소는 **약별 하루 단위**로만 표시한다. 다음 복용 시간은 안내 정보이며 그 시간에 대한 독립 완료 상태로 취급하지 않는다.
- **후속 작업:** 시간별 완료가 제품 요구라면 로그에 예정 시간 또는 일정 ID를 저장하는 계약, 기존 기록 마이그레이션, 중복 방지 키, 화면/알림 동기화 방식을 먼저 정의해야 한다.

## 2. 통계의 분모와 기간

- **시안 기대:** 이번 주 `완료 18/21회`처럼 예정된 모든 복용 횟수를 분모로 계산하고 약별 기록을 보여준다.
- **현재 계약:** `useStats.ts`는 최근 7일의 고유 `medication_id` 로그 수를 **현재 등록된 약 전체 개수**로 나눈 일별 비율만 반환한다. 복용 요일, 하루 여러 시간, 과거에 추가/삭제한 약의 당시 일정은 반영하지 않는다. 약별 7일 완료 횟수와 실제 예정 횟수도 반환하지 않는다.
- **이번 구현:** 통계 화면은 `최근 7일 기록 비율`과 `현재 등록된 약 N개 기준`을 명시한다. 시안의 `18/21회`, 전주 대비 수치, 근거 없는 성취 배지는 표시하지 않는다.
- **후속 작업:** 기간별 일정 스냅샷 또는 날짜별 예정 복용 항목을 계산하는 계약과 집계 API가 필요하다. `useStats`가 조회 오류를 빈 배열로 바꾸는 점도 오류 상태를 구분할 수 있게 개선해야 한다.

## 3. 저장소의 서버 스키마 문서와 실제 프런트엔드 요청

- **현재 코드 차이:** `lib/db/src/schema/medications.ts`의 Drizzle 정의에는 `time`, `category`가 있지만 프런트엔드 `medicationRepository.ts`는 `times`, `days`, `memo`, `user_id`를 읽고 쓴다. 로그 삽입도 `user_id`를 전송한다. `docs/architecture.md`의 테이블 설명 역시 현재 프런트엔드 모델과 다르다.
- **이번 구현:** 데이터 구조와 요청 필드는 변경하지 않았다. 기존 Supabase 환경에서 동작하는 프런트엔드 계약을 유지했다.
- **후속 작업:** 운영 Supabase 테이블/인덱스/RLS를 확인하고 Drizzle 스키마, 타입, 아키텍처 문서를 실제 계약에 맞게 동기화해야 한다. 이 확인 전에는 스키마 마이그레이션을 실행하지 않는다.

## 4. 알림과 오프라인 상태

- **현재 계약:** `useNotifications.ts`는 Capacitor 네이티브에서만 알림을 예약한다. 브라우저에서는 알림 토글이 저장돼도 알림은 오지 않는다. 권한 거부와 예약 실패는 사용자 화면에 전달되지 않는다. 약 저장은 Supabase 요청에 의존하며 오프라인 큐가 없다.
- **이번 구현:** 복용 알림 설정은 유지하고 복약 기록 실패 시 기존 토스트/재시도 흐름을 보존한다. 웹 알림이나 오프라인 저장을 제공한다고 새로 약속하지 않는다.
- **후속 작업:** 웹 알림 지원 여부, 네이티브 권한 상태 표시, 오프라인 저장/재시도 정책을 제품 범위로 결정해야 한다.
